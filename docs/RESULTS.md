# Results

MovieLens-1M, implicit feedback (ratings 4-5), per-user leave-last-out split, 6,035 test users,
full ranking over all 3,706 movies with each user's history excluded (no sampled negatives).
Values are test-set point estimates with 95% bootstrap confidence intervals over users (1,000
resamples). Tables between `<!-- table:... -->` markers are generated by
`experiments/make_results.py` from the per-user rankings saved under `results/`.

## Retrieval: the ceiling for ranking and the cost of approximation

The ranker can only reorder what retrieval returns, so retrieval Recall@200 bounds what the
two-stage system can reach in its top 200. Latency is per user, one thread, for retrieving
200 fresh candidates (the request asks for 200 plus the user's history size).

## Analysis

**Two-tower retrieval beats every baseline.** Exact two-tower retrieval improves on tuned
implicit ALS by +0.0170 NDCG@10 [+0.0122, +0.0217] and +0.0323 Recall@10 [+0.0239, +0.0406]. It
also recommends a far wider range of movies: 50.1% of the catalog appears in someone's top 10,
against 21.8% for ALS and 3.1% for popularity. The log-Q correction is designed to counter the
popularity bias of in-batch training; its contribution is isolated in the ablations
(`docs/ANALYSIS.md`, milestone B7).

**Approximate retrieval costs almost nothing.** Serving the two-tower model from hnsw-engine instead
of exact search keeps 98.4% of the exact top-200 and lowers Recall@200 from 0.6171 to 0.6131. The
top of the ranking is unaffected: the paired NDCG@10 difference is +0.0004 [+0.0001, +0.0007].
That tiny gain is an artefact: when the index misses a non-target movie that exact search ranked
above the target, the target moves up one place. Missing the target itself shows up in Recall@200.

**At this catalog size exact search is faster.** Exact scoring of 3,706 movies takes 0.046 ms per
user; hnsw-engine's compiled engine takes 0.094 ms, FAISS HNSW 0.13 ms and the pure-Python engine
1.07 ms (one thread). The compiled and pure-Python engines return identical candidates for every
user, as their graphs are identical. Graph search
pays off for catalogs of millions of items (see the hnsw-engine benchmarks); here the index
demonstrates the production serving path and measures its accuracy cost.

**The ranker adds +0.0287 NDCG@10, but only after a negative result.** The final ranker improves
on retrieval order by +0.0287 NDCG@10 [+0.0243, +0.0332] and +0.0477 Recall@10 [+0.0401, +0.0555].
It was not the first attempt. The brief's feature list alone (two-tower score and rank, popularity
before the request, year, genre affinity, activity, demographics) scored *below* retrieval order:
NDCG@10 0.057 against 0.062 on its one test evaluation (`results/ranker/first-attempt-base-features`).
Diagnosing on validation data only showed why: on a selection set of 362 validation users the base
features reached 0.094-0.104 NDCG@10 under three LightGBM settings, against 0.109 for retrieval
order (`results/ranker_tuning/main/tuning.json`). The ranker had nothing the two-tower score did not
already know, and the extra splits added noise. Adding four recency features (cosine similarity of
each candidate to the user's latest movie and to the five latest, and the movie's age at request
time) lifted the selection score to 0.148. The two-tower user vector averages up to 50 past movies
and cannot express what the user watched *last*; viewing comes in bursts of a genre or franchise.
By gain, the most important features are the retrieval rank, similarity to the latest movie and
popularity before the request; gender and age contribute nothing.

**The ceiling.** The ranker can only reorder the 200 candidates; the target is among them for 61.3%
of users (hnsw-engine Recall@200 0.6131). Raising that ceiling (more candidates or better retrieval)
bounds what any ranker can achieve.

**What to keep in mind.** All numbers use the standard per-user leave-last-out protocol, in which
models see other users' later interactions; absolute values may be slightly optimistic, while
comparisons between methods are fair because every method sees the same data. The ranker was
evaluated on test twice (first attempt and final configuration), and both results are reported
here; all choices in between used validation data only. Validation targets serve both the
two-tower model's early stopping and the ranker's training labels, so the ranker sees a slightly
optimistic two-tower score during training; if anything this works against the ranker on test.

*Findings.*

1. **The conclusions transfer.** With every setting carried over from ML-1M, the methods rank in
   the same order as on ML-1M, except that exact and approximate retrieval swap places (they
   differ by 0.0004 NDCG@10 on either dataset). The two-tower model beats tuned implicit ALS by
   +0.0285 NDCG@10 [+0.0269, +0.0300], the ranker adds +0.0243 [+0.0230, +0.0255] over retrieval
   order, and the full system reaches 0.1047 [0.1030, 0.1066] against 0.0524 [0.0511, 0.0536] for
   ALS.
2. **Much tighter intervals.** With 69,613 test users instead of 6,035, the full system's NDCG@10
   interval is [0.1030, 0.1066], against [0.0848, 0.0959] on ML-1M.
3. **The index costs a little more on a larger catalog, and is still not needed.** hnsw-engine
   keeps 97.7% of the exact top-200 (98.4% on ML-1M). The loss is measurable in Recall@10 (-0.0015
   [-0.0022, -0.0008]) but not in NDCG@10 (-0.0004 [-0.0008, +0.0000]). At 10,677 movies exact
   search is as fast as the index (0.2029 against 0.2005 ms per user; measured with a one-minute
   load average of 3.8 at the start of the run, `results/retrieval/ml10m/environment.json`, so read
   the latencies as rough). The candidates come from the compiled engine here (on ML-1M from the
   pure-Python engine; the two return identical candidates).
4. **ALS needed its own regularisation.** The ML-1M optimum (30) was not ML-10M's: three validation
   passes found 100 (`configs/ml10m/baselines.yaml` lists every point). Even tuned, ALS recommends
   from a narrow slice of the catalog (coverage@10 0.0812, against 0.4980 for the full system).
5. **The ranker leans on the same signals.** By total gain, the retrieval rank leads, followed by
   popularity over the last 30 days, the two-tower score, popularity before the request, user
   activity and similarity to the latest movie; genre affinity contributes least
   (`results/ranker/ml10m/metrics.json`). Training took 409.5 s on 42,808 users.
